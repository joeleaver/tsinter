## SILENT: U2-FD-02 (#82), wasm-native host rows (intermittent)

- Test: `tests/harness/wasmnative-host-rows.test.ts > the wasm lane's host rows on the wasm-native lane (214 rows) > U2-FD-02 (#82)`. This is the wasm lane's row `U2-FD-02 fd 0 in the stdout slot: the child's write fails with SIGPIPE, as under the harness's Node (exit null)`, run on the wasm-native lane.
- Program: `spawn("/bin/sh", ["-c", "echo to-slot1-fd0; echo status=$? >&2"], { stdio: ["ignore", 0, 2] })`, then it prints `b exit <code>` on `exit`.
- Node stdout: `b exit null\n`
- Actual (wasm-native) stdout: `b exit 0\n`
- stderr: the row doesn't compare stderr for this case. Exit codes were not reached, because the stdout assertion failed first. There was no tsinter diagnostic.
- How often: failed once, in stage f (full suite, all 4 workers busy). It passed in stage d, and passed 6 of 6 times alone. The wasm-lane copy of the row (`wasm-differential.test.ts`) passed in both c and f.
- Likely cause: the harness's `run()` calls `p.stdin.destroy()` right after spawn, so the program's fd 0 is a socket whose peer is supposed to be gone before anything writes to it. Then the grandchild's `echo` to fd 0 dies of SIGPIPE, and the exit code is `null`. `b exit 0` means the write succeeded, so the peer was still open when the grandchild wrote. That fits a load-dependent race between the harness closing stdin and a fast-starting native binary. It does not fit a code-generation fault. This commit only changes how `--dynamic` builds TS literals, and this row is a plain build. Even so, the row is not on the known list, so it counts as NEW.
